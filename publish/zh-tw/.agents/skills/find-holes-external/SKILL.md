# find-holes-external — 外派找漏洞

你是 hub。本 skill 把規劃書的指定範圍派給**外部模型**做找漏洞審查。
**spoke 產出意見，不產裁決；採不採用由使用者決定。**

工具是 `dowafu`（已全域安裝的本地 CLI），用你的終端機工具呼叫。
**spoke 只讀你給它的東西**——唯讀，而且每次讀檔都經白名單判定。

> **需要知道的全部在這裡，不要去翻別的文件找補充說明。**

---

## 1. 前置檢查

**一、確認 lens 定義讀得到。** 讀 `.claude/agents/hole-finder-*.md`，回報你看到哪幾支、
各自是什麼視角。讀得出來就算過。

**讀不到就停下來告訴使用者，不要自己去別處找、也不要憑空寫一份。** 那些檔是 spoke 的
system prompt 來源——角色、禁令、輸出格式、收尾句都在裡面。自己寫的版本會讓 spoke 的
產出跟稽核判準對不上。

**二、確認 `tmp/` 有被 git 忽略。** spoke 的回報會含規劃書原文，不該進版控。
沒被忽略就停下來問使用者要不要加，**不要自己改 `.gitignore`**。

## 1.5 執行層面的四件事

**工單格式、逐題對照表、判讀紀律都跟你在哪執行無關**，那些寫在後面的流程步驟裡，
一律照辦。這一節只講**執行層面**。

**一、每一條 `dowafu` 指令都照這個形狀，`cd` 與 `--repo-root .` 都不要省：**

```bash
cd <repo 根的絕對路徑> && dowafu <工單目錄> --repo-root . --dry-run
```

**`--lang` 決定 CLI 輸出與 spoke prompt 的語言，預設是 `en`。** 你裝的是中文套件、lens 檔也是
中文的，所以**中文專案要帶 `--lang zh-tw`**——不帶的話 CLI 會用英文輸出，spoke 也會拿到英文
prompt，而**兩邊都不會報錯，只是安靜地混語**。不想每次打，可以設環境變數 `DISPATCH_LANG=zh-tw`；
優先序是 `--lang` > `DISPATCH_LANG` > 內建預設 `en`。

你的終端機不保證落在哪一個 workspace folder，而 `--repo-root` 預設取 cwd。cwd 錯了會
**安靜地錯**——工單照樣解析、spoke 照樣派出去，只是白名單邊界與 lens 定義都指到別處。

**二、`dowafu` 是外部全域 CLI，不在 workspace 裡。不要去找它，直接下：**

```bash
dowafu --version
```

印不出版本號只有兩種情況，**兩種都不要自己搜檔案系統**：

- **`command not found`**——問使用者 CLI 裝在哪（請他跑 `which dowafu`），拿到絕對路徑
  之後改用絕對路徑呼叫
- **`Operation not permitted`**——**沙箱擋的，不是沒安裝**。它多半裝在家目錄底下，而沙箱
  預設不讀家目錄。照 host 的提示放行再跑一次；API key 與對外網路同樣被擋，所以放行是
  必要的，不是可選的

**三、`--yes` 一定要帶。**

不帶的話 CLI 會印出 `繼續？[y/N]` 停住等輸入，而你的 host 會把控制權交回給你，並提供一個
**send input** 選項——**那條路能把 `y` 送出去，直接開始計費**。

> **不准選它。** 加 `--yes` 等於代替使用者按下確認，加之前必須在對話裡取得他的明確同意。

**四、實跑用背景執行，進度靠檔案而不是終端機輸出。**

用檔案讀取工具輪詢 `tmp/spoke/<ticket-id>/run.jsonl`：CLI 逐事件寫入該檔，讀得出跑到
哪一輪、有沒有 `round_error`。**完成判定見 §5**——「兩個 `spoke_end`」只是其中一半。
背景終端機的輸出不保證拿得到，而單支 spoke 可能跑上好幾分鐘。

> **把終端機當啟動器，不要當資料通道。**

> 本節用功能稱呼工具（「終端機工具」「檔案讀取工具」），因為工具名依版本與模型而異——
> 對不上是常態，照你手上實際有的那個用。

## 2. 提派工計畫，等使用者確認（**確認前不准派**）

| 要列的 | 說明 |
| --- | --- |
| 待審段落 | 哪個檔案的哪一節、幾行 |
| 派幾個 spoke、哪些 lens | 見下 |
| 每個 spoke 的 provider／model | 見下 |
| **每題的「問題 → 答案在哪個檔 → 在清單裡嗎」對照** | **必列，見下方格式** |
| 預估成本量級 | 參考值：三個 spoke、中等工單約 40k token |
| **每支 spoke 的產物落點** | **必列**，見下方〈幾支 spoke 就要幾個落點〉 |

### 具體問題與允許清單**必須逐題對照著列**

不要把「問題」和「允許清單」分成兩塊各列一遍——那樣看不出哪一題沒有對應的檔案。
用這個格式：

| Q | 問題 | 答案在哪個檔 | 在清單裡嗎 |
| --- | --- | --- | --- |
| 1 | §3.1 的 schema 變更可行嗎 | `prisma/schema.prisma` | ✅ |
| 2 | §2 現況描述與實際程式碼有無出入 | `lib/a.ts`、`lib/b.ts` | ❌ **要補** |

**這是最常犯的錯**：問了某題，卻沒給回答那題所需要的檔——問「這是不是唯一入口」卻沒給
該檔本身，問「現況描述有無出入」卻只給了「新宣稱所在的檔」。spoke 只能在「無法驗證」欄
記下缺什麼，**那是派工端的失誤，不是它的問題**。

逐題列出來，使用者一眼就能看出漏了什麼。**這一欄不是形式，是這個 skill 目前唯一擋得住
漏檔的機制**——`--dry-run` 檢查得了格式，檢查不了「問題與清單對不對得上」。

**使用者對數量／模型／lens／問題的修改一律照辦。**

**裁允許清單時，逐題自問：「這一題的答案在哪個檔？那個檔在清單裡嗎？」** 按 lens 的
名稱配檔案（safety 就給安全相關的）會配錯——lens 是**看的角度**，清單是**看的材料**。
清單全給了某問題的**產生端**、而問題問的是**顯示端**時，spoke 物理上不可能答對；
換一批對準答案位置的檔案，同一個 lens 就抓得到。**這個自問是為了在派工前擋下落差，
不是派工後才發現。**

### 每支 spoke 各一張表——而且**那張表本身就是交件物，不是「我有做」的宣告**

**那張表每支 spoke 各填一張，而且兩張都要攤在使用者面前。** 說「清單都對過了」「該有的檔都在」
**不能取代把表給他看**——「允許清單已涵蓋所有問題」只是一句話，真假都一樣好寫。

每一列要寫**你實際預期答案所在的那個檔的路徑**——不是目錄、不是「tags 那幾支路由」、
不是 lens 的名字。寫成與允許清單同樣的形式，兩邊才對得起來：

| Q | 問題 | 答案在哪個檔 | 在清單裡嗎 |
| --- | --- | --- | --- |
| 1 | `requireAuth` 回傳的 userId 夠不夠做刪除自己的檢查 | `lib/auth-guard.ts` | ✅ |
| 2 | 最後一位管理員的防護是不是原子的 | `prisma/schema.prisma`（其餘看待審段落本身） | ✅ |

**把路徑寫進那一欄之前，先確認答案真的在那個檔裡**——grep 那個符號，或直接開檔。
這一欄是為了在派工前擋下漏檔；**憑印象填的話它什麼都擋不住**：一個看起來很合理的檔名，
與正確的那個一樣能通過格式檢查，而差額是 spoke 用錢付的。

**兩支最後拿到同一批檔也可以，但要說得出為什麼。** 清單相同是**可以解釋的結論**，不是起點；
而「裁到兩份不一樣為止」是同一個錯誤的反面。

**一份清單餵兩支 lens，會往交集收斂，而不是聯集。** 最先掉的是「只有其中一支需要」的檔，
而那正是那支 lens 被派去看的東西；spoke 這時只能把缺口寫進「無法驗證」欄，而用這種方式
發現要付一整輪派工的錢。為省錢裁清單是合理的——但要**各自對著自己的問題裁，不是對著另一支裁**。

### 幾支 spoke 就要幾個落點——先挖好坑再派

一支 spoke 的產物落在 `tmp/spoke/<ticket-id>/` 底下**以它的 agent 為名的那一組檔**：
`<agent>.md`，以及 `raw/<agent>.request.json`／`.response.json`／`.errors.json`。
那一組同進同出，所以**落點就是 `<ticket-id>` ＋ `<agent>` 這個組合**。

**派工計畫要逐支列出落點路徑，判準只有一句：落點數要等於 spoke 數，而且兩兩不同。**

| spoke | lens | provider／model | 產物落點 |
| --- | --- | --- | --- |
| 1 | safety | openai／gpt-5.6-luna | `tmp/spoke/auth-review-luna/hole-finder-safety.md` |
| 2 | safety | deepseek／deepseek-v4-flash | `tmp/spoke/auth-review-ds/hole-finder-safety.md` |
| 3 | feasibility | gemini／gemini-3.6-flash | `tmp/spoke/auth-review-luna/hole-finder-feasibility.md` |

**兩支算出同一個路徑，就是坑不夠**——而且解法不是改個檔名，是**拆工單目錄**：同一個 lens 要跑
多個型號時，一個型號一個目錄（ticket-id 加後綴），各派一次。
不同 lens 共用一個目錄沒有問題，它們的 agent 名本來就不同。

這一欄要用數的，不要用看的。**你不需要知道撞名會發生什麼**——數不對就先停下來拆目錄。

### lens

| agent | 視角 |
| --- | --- |
| `hole-finder-safety` | 安全、併發競態、失敗態 |
| `hole-finder-cost` | 成本閘門、計費呼叫順序、資源消耗上限 |
| `hole-finder-feasibility` | 可行性、可實作性、規格與實作的落差 |

派一個也可以，三個都派也可以。**不要因為「這個 lens 好像不適用」就先排除**——cost lens
對一個沒有任何計費呼叫的專案，照樣找得出「無登入端點的資源消耗無上限」這類問題。

### 型號（只有這些，填錯會被擋下）

| provider | model |
| --- | --- |
| `openai` | `gpt-5.6-luna`／`gpt-5.6-terra`／`gpt-5.6-sol` |
| `deepseek` | `deepseek-v4-flash`／`deepseek-v4-pro` |
| `gemini` | `gemini-3.1-flash-lite`／`gemini-3.5-flash-lite`／`gemini-3.6-flash` |
| `anthropic` | `claude-opus-5`／`claude-sonnet-5` |

### 使用者沒指定型號時

**提一組，說明你依據什麼提**（成本量級、素材規模、這個 lens 需不需要深推理），然後
**等他確認**。不要自己決定就派；他改過之後也不要因為「另一個好像比較好」就換回來。

型號怎麼取捨是使用者的專案決定，這份文件不替他決定。

## 3. 寫工單

寫到 `tmp/dispatch/<ticket-id>/`，`<ticket-id>` 用主題 slug（例如 `auth-review`）。

### `_dispatch.md`

```markdown
<!-- format: v1 -->
# dispatch <ticket-id>

| agent | provider | model | effort |
| --- | --- | --- | --- |
| hole-finder-safety | openai | gpt-5.6-luna | |
| hole-finder-cost | deepseek | deepseek-v4-flash | |
| hole-finder-feasibility | gemini | gemini-3.1-flash-lite | |
```

首行 `<!-- format: v1 -->` **必須有**；`model` 必填；只列你要派的那幾個。`effort` 留白
即為 **`high`**——四家的 `reasoning.default` 目前都是 `high`。要調就查
`providers.json` 的 `reasoning.allowed`，**各家值域不同**（例如 `deepseek` 沒有
`medium`）；填了不在值域內的值會被擋下並列出允許值，不會靜默降級。

**agent 欄在同一份 `_dispatch.md` 裡不得重複。** 一個 agent 一列；要用同一個 lens 跑多個型號，
拆成多個工單目錄（見 §2〈幾支 spoke 就要幾個落點〉）。**CLI 在解析期就會擋下重複的 agent，
乾跑一樣會被擋**——但那是最後一道防線，不是可以省掉數落點那一步的理由。

### `_shared.md`（所有 spoke 共用）

```markdown
# 前提（不受審）
- <一行結論，例如「採 JWT 無狀態驗證，已定案」>
- <沒有就寫「無」>

# 待審段落
<把規劃書段落逐字貼進來，不要摘要、不要改寫>
```

**待審段落一定要逐字內嵌**，不能寫「見 `_docs/xxx.md` 第 3 節」——spoke 讀不到 `_docs/`
（那是禁區，白名單會拒絕）。

### `<agent>.md`（每個 spoke 一份，檔名要跟 `_dispatch.md` 的 agent 欄一致）

```markdown
# 具體問題
1. <問題>
2. <問題>

# 允許讀取
- src/foo.ts
- lib/bar.ts
```

**四條規則**：

1. **不要寫角色定義**（「你是一個…」「不得…」「請以…收尾」）。角色、禁令、輸出格式、
   收尾句由 `dowafu` 從 `.claude/agents/<agent>.md` 讀出來組進 system prompt。
   寫進工單會造成規則雙來源——同一組規則出現兩次、措辭還不一致。

2. **問題要開放，不要指向你已經發現的東西。** 把答案寫進問題，spoke 找到就只是複述工單。

3. **允許清單要涵蓋「回答這些問題實際需要的檔案」。** 逐題自問：要回答這題得讀哪些檔？
   漏了的話 spoke 只能在「無法驗證」欄記下缺什麼——**那是派工端的失誤，不是它的問題**。
   路徑**相對 repo 根目錄**。留空也合法（純文字審查），但那樣就讀不到程式碼，會少掉
   「文件說 X、`src/foo.ts:42` 其實是 Y」這類最有價值的發現。**清單屬於這一份
   `<agent>.md`，不屬於整批派工**——不要把另一支的清單整份複製過來：對它有用、對這一支
   沒用的檔，在讀取順序裡是純負擔；反過來就是漏洞。**沒開過的檔不能拿來證明「答案不在
   那裡」**——如果你指不出某一題的答案在哪個檔，那一題現在就是沒有檔可依，不管表上填了什麼。

4. **大的檔案排在清單最後——這能省掉一半成本。** spoke **嚴格照清單順序**讀檔，而多數
   模型**一輪只叫一個檔**，每一輪又會把先前讀過的全部內容重送一次。所以一個檔被重複
   計費的次數 ＝ **總輪數 − 它被讀的輪次**——**排越前面，被重送越多次**。
   一個十幾 k token 的大檔，排第一 vs 排最後，該 spoke 的總量可以差到將近一倍。
   做法很簡單：**依檔案大小遞增排列**，最大的放最後。不確定大小就先 `wc -l`。
   **打亂清單順序時這條仍然適用**——大檔壓最後，只洗其餘。

### 跑 2–3 次怎麼做

一次派工只是一次抽樣。**同一組設定跑 2–3 次，取聯集。**

- ticket-id 加後綴（`<主題>-r1`／`-r2`／`-r3`），**每一次一個獨立目錄**
- **第二次先用逐字相同的工單**，只換 ticket-id
- **比對前兩次的結果，再決定第三次怎麼跑**：
  - 出現明顯的新條目 → 這個型號直接重跑就有效，第三次照樣逐字重跑
  - 幾乎是同一組 → 這個型號對相同的 prompt 會收斂，**不擾動就拿不到新東西**。
    第三次改成**重排允許清單順序**，問題與 `_shared.md` 逐字不動

重排時**大檔仍然壓在最後**（見上方規則 4），只洗其餘。

## 4. 先乾跑（不花錢）

**這是花錢之前唯一的檢查點。** 工單一旦真的派出去就開始計費，中途失敗或中斷，錢也拿
不回來——**沒有 resume，重跑等於重新付一次**。乾跑錯了改一改再跑，不花任何錢。
**所以這一步不能跳過。**

它抓得到的：`repoRoot` 指錯專案、型號填錯、lens 定義找不到、允許清單裡的檔不存在、
`tmp/` 沒被忽略、估算超過閘門上限——這些在真的呼叫 API 之前就會被擋下來。

**另有一項不擋、只警告**：待審段落疑似被內嵌文件的 `#` 標題切斷時，報表會多印一行 `⚠`
（形態與怎麼辦見下方報表項目表）——乾跑本身照樣算通過，錢也還沒花，但它擋的是「付全額、
審半份」，優先序與上面那些一樣高。

> 其中 lens 定義與 `tmp/` 你在第 1 節已經確認過了。這裡不是要你重做一次，是讓你知道
> **就算第 1 節漏了，這一關還會擋下來**——但反過來不成立，所以第 1 節照樣要查。

**它抓不到的是工單內容本身**：問題問得好不好、允許清單對不對得上那些問題，乾跑一律看
不出來。那是你在第 2 節就該做完的事（逐題對照表），乾跑不會替你補。

```bash
dowafu tmp/dispatch/<ticket-id> --repo-root . --dry-run
```

**一次乾跑只驗一個工單目錄。** 這一批如果拆成了多個目錄（同一個 lens 跑多個型號時就會），
**每一個都要各乾跑一次**，並把各次的估算**加總**之後再把數字呈給使用者。
只乾跑第一個就去實跑，等於其餘目錄完全沒經過這道檢查。

**跑之前先跟使用者說明這一步在幹嘛。** 他多半沒用過這個工具，看你在下指令會以為已經
開始派工、開始計費了：

> 這一步只解析工單、驗證設定、估算用量，**不呼叫任何 API、不產生任何費用**。
> 目的是在花錢之前，先確認要派出去的東西是對的。

**跑完把報表轉述給他**，不要只說「乾跑通過」。至少這幾項：

| 報表項目 | 要讓使用者看懂的 |
| --- | --- |
| `repoRoot` | 指到的是不是他的專案 |
| `model`／`effort` | 每個 spoke 實際會用哪個型號 |
| 初始 prompt 估算 | 一開始就會送出去的量 |
| 允許清單估算 ＋ 檔數 | spoke 讀得到哪些東西、多大 |
| 最壞總消耗 | **這是上限不是預期值**（各 spoke 的 cap 加總），實際通常遠低於此 |
| `⚠ 待審段落…可能被切斷` | 把內嵌文件的 `#` 標題降成 `##`，或改用四重反引號圍籬包住——三重圍籬包不住自帶三重圍籬的內嵌文件。組工單章節已交代過這條，這裡是二次提醒 |

**用自己的話、用表格轉述——除非你是逐位元組貼上原輸出，否則不要放進 code fence。**
code fence 的語意就是「這是工具印出來的」，把改寫過的內容裝進去，等於宣稱一個你其實
沒做到的準確度。改寫沒有問題，而且常常比原輸出好讀；把改寫冒充成原輸出才有問題。

**要轉述就連限定語一起轉。** 報表裡那些限定語，正是讓數字不會被誤讀的部分——總量是上限
而非預期值、價目取自哪一天、估算建立在什麼假設上、每支 lens 收尾句的確認行。它們看起來
最像可以省的，卻正是讓這些數字能拿來做決定的東西。**限定語一刪，你交給使用者的數字就
比工具給你的更硬。**

**工具標了 `⚠` 或 `ℹ` 的那幾行一律逐字轉述，不得改寫。** `⚠` 是工具在說「現在有事」——
輸出目錄已經有產物、清單順序正在多花錢、某支 spoke 什麼都沒讀。把它改寫成一句比較平順的話，
是你能對這份報表做的最貴的一件事，因為讀者會失去唯一那個「需要你做決定」的訊號。
特別是：`⚠ 大檔排清單最後可降至 N（本項省 N%）` 的意思是**你現在沒有排好**，
不是「已經排好了、重排只能再省一點」。

必須跟著數字一起活下來的限定語，逐項點名：

| 出現在哪 | 什麼一定要跟著轉 |
| --- | --- |
| 每支 spoke 那一行 | `effort=`、`lang=`、`store=`，以及它的 `cap` |
| 單價子行 | 每 M token 的數字**與**`價目查證日 <日期>` |
| `ℹ` 收尾句檢查 | 每支一行，照印的轉 |
| 初始 prompt 估算 | 它**不含工單與允許清單**，以及閘門上限 |
| 允許清單估算 | 它是上限、**不去重**，以及字元／token 的換算基礎 |
| 逐個讀順序放大量 | 它是「逐個讀假設下的上限、批次讀的廠牌不適用」、排序的判定，以及**本項不含初始 prompt 與工單** |
| 最壞總消耗 | 它是**上限不是預期值**，且是各 spoke cap 的加總 |

少了這些，數字讀起來會比工具的原意更硬。**自己把 token 換算成錢時，要講明那是你算的、依據哪一行單價。**

報表只給 token，不給金額，且**只在乾跑階段成立**。要換算成錢，**價目來源是
`providers.json` 的 `pricing`（`inputPerM`／`cachedInputPerM`／`outputPerM`），不要查
官網**——那份數字就是 CLI 計費用的，查官網會讓「你報的錢」與「CLI 算的錢」對不上。
`pricingSource.asOf` 看起來過舊就回報使用者，不要自行改數字（要改是改
`providers.json`）。**實跑**的 `summary.md` 有「估算成本」欄，每支 spoke 結束也會印
一行 `cost=`，那是 CLI 自己算好的金額，**直接轉述即可，不必自己算**。

然後逐項核對：`repoRoot` 是這個專案、`model` 跟你寫的一致、**報表印出的 `effort` 是
你預期的那一級**、估算 token 量級合理、**沒有 `⚠ 輸出目錄…未被…忽略` 的警告**。

任何一項不對就修工單重跑，**不要往下走**。

## 5. 實跑

**輸出目錄必須是一個還不存在的目錄。** 先看 `tmp/spoke/<ticket-id>/`：已經有東西了就
**換一個新的 ticket-id 派出去**——換 id 不花錢，碰撞這件事就不存在了。

**刪產物是使用者的決定，永遠不是你的。** 派工前不行、順手整理不行、「它擋路」也不行。
你可以問要不要清掉，但不可以自己清，也不可以直接跑上去。那底下的東西是花錢買來的，
而目錄本身不會告訴你使用者還要不要它。（第 7 節的清理是另一回事：那是**裁決之後**、
他說了才做的。）

**這條有 CLI 撐著。** 目錄非空時它會在派工前中止——沒呼叫任何 API、沒花任何錢——
並要你換一個 ticket-id。**沒有可以蓋過它的旗標**：清目錄是使用者的動作，
不是你能帶的參數。

CLI 開跑時會清空 `run.jsonl`（舊事件會讓你數錯），**但那一步只在它真的跑起來時才執行**。
啟動失敗的話，上一次的產物原封不動留著——而**檔案不會告訴你它是不是這一次的**。

```bash
dowafu tmp/dispatch/<ticket-id> --repo-root . --yes
```

> **這一步會花錢。** `--yes` 等於你代替使用者按下確認，**加上它之前必須在對話裡取得
> 使用者的明確同意**。
>
> 不帶 `--yes` 會停住等輸入（見 §1.5 第三條）。不論如何都不會花到錢——確認通過之前
> CLI 不呼叫任何 API。

> **單支 spoke 可能跑到十分鐘，而且快慢無法事先判斷**——同素材、同工單、token 量級相近，
> 兩次的耗時仍可能差好幾倍。那是對方伺服器的負載，不可歸因、也不可預測。
>
> **`--timeout` 是單次 API 呼叫的逾時，不是整支 spoke 要跑多久**——一支 spoke 內有多輪
> 呼叫，它不會限制總時長，不要拿它來估整支要跑多久。
>
> **前景執行本身另有外部工具的逾時上限**（十分鐘量級），與 `--timeout` 無關、擋不住。
> **預估這次會跑久（清單大、問題多、選了較慢的型號）就改背景執行**，不要在前景硬等。

### 啟動確認：先確認它真的跑起來了，再開始等

**下指令之前先記下當下時間**（`date -u +%Y-%m-%dT%H:%M:%SZ`），下完隔十幾秒讀一次
`tmp/spoke/<ticket-id>/run.jsonl`：

| 讀到 | 判定 |
| --- | --- |
| 檔案不存在 | **沒跑起來**——CLI 一開跑就會建它，這不是「還在等 API」 |
| 有 `spoke_start`，`ts` 晚於你下指令的時刻 | 起來了，開始輪詢 |
| 有內容，但 `ts` 早於你下指令的時刻 | **沒跑起來，你讀到的是上一次的產物** |

`ts` 是每一行都有的 ISO 8601 時間戳，**這是判斷「這一份是不是這一次」的唯一機械依據**。

**沒跑起來就不要繼續等。** 這個失敗形態自己看不出來：舊產物的兩個 `spoke_end` 都是
`succeeded`，格式、稽核欄、成本全部正常，唯一的破綻是時間戳。

### 等多久算不正常

**看的不是總耗時，是 `run.jsonl` 有沒有在長。** 單支 spoke 跑上十分鐘是正常的，但
**十分鐘之內一定會有新事件寫進來**——單次 API 呼叫的逾時預設就是十分鐘，而逾時與重試
各自都會寫一行 `round_error`。

> **超過十分鐘沒有任何新事件，就停下來告訴使用者**，不要繼續等、也不要自行重跑。
> 把最後一個事件與它的 `ts` 一起報給他，讓他判斷。

**進度一律以 `run.jsonl` 為準**——CLI 逐事件寫入該檔，中途 Ctrl-C 也讀得出跑到哪。
終端機那條通道不保證拿得到（見 §1.5 第四條），`run.jsonl` 不受影響。

**跑完的判定是兩件事同時成立**：兩個 `spoke_end`，**而且**這份 `run.jsonl` 通過了上面的
啟動確認。只看 `spoke_end` 會把上一次的產物當成這一次的結果。

**真的撞到失敗或逾時：要不要重跑由使用者決定，不要自行重跑。** 重跑是重新付費，中斷前已
花的錢救不回來（沒有 resume 機制）。把中斷時的狀態（`run.jsonl` 讀到哪、失敗訊息）告訴
使用者，讓他判斷要不要重來——這與「零讀取就整份重跑」不衝突：那條是「判定沒跑」，這裡是
「跑了但被中斷」，成本結構不同。

## 6. 回收——摘要優先，原文為例外

產物在 `tmp/spoke/<ticket-id>/`：`<agent>.md`（原文）、`summary.md`（稽核表）、
`run.jsonl`（執行記錄）、`raw/`（完整請求與回應）。

**`run.jsonl` 是逐事件附加寫入的，不會被覆蓋。** 產物與 `raw/` 若被蓋掉——重跑，或另一支
寫到同一個名字——那個檔裡仍然留著每一支的 `spoke_start`（provider 與型號）、逐輪 usage、
每一次讀檔（含被拒的）、錯誤，以及 `spoke_end` 的 token 與成本。
**報告文字救不回來，但花了多少錢、讀了哪些檔，可以還原。**

> **回收之前先確認 §5 的啟動確認過了。** 這個目錄底下的任何檔案，都不會告訴你它是不是
> 這一次的產物。

**呈現順序不得更動**：

1. **逐個 spoke 的內容都要讓使用者看到**，標明 lens 與模型。**摘要是預設**，滿足以下
   四個必要條件：
   1. **明確宣告取捨**——在摘要開頭寫明「本節為摘要，非逐字照登」，不安靜地摘掉
   2. **判讀涵蓋每一條，無一略過**——每個 spoke 的每一條觀察都要在後面的「hub 判讀」出現，
      這是取代「原文照登」的可稽核性來源：原文不在你眼前列出，不代表它沒被看過
   3. **指出原文路徑**（`tmp/spoke/<ticket-id>/<agent>.md`），使用者隨時可自行比對
   4. **只在產物尚未清理時才成立**——第 7 節清掉之後就沒有底本可查
   > 這條規則要防的不是「沒有原文」，是**防止 hub 只挑對自己有利的講**。滿足以上四件事，
   > 手段換成摘要也一樣防得住；換句話說，要守住的是目的，不是「原文」這個手段本身。

   **原文照登用於兩種情形**：產物已被第 7 節清掉（沒有底本可查，摘要不成立），或單份
   規模小到摘要反而多此一舉。除此之外都走摘要。

   **做不到第 2 條就不要派這麼多 spoke**——問題出在派工規模，不在呈現方式；不要拿
   「沒把握」當理由退回整份照登。
2. **`summary.md` 的稽核欄轉述進上面那一節——它印出來的每一段都要點名。** 每支 spoke
   一段一行，**順序照 `summary.md` 印的**：`工具呼叫` 在最前面，排在 `收尾句` 之前。
   某一段是空的時候，CLI 會自己印它的空值字（中文那套印 `無`），**照它印的抄，
   而且一段都不准漏掉**。全部寫出來不比只寫大部分貴，而少一個段名使用者看得出來，
   少一列他看不出來。

   **`⚠` 開頭的那幾段不准省，`(無法稽核)` 也不准省。** 它們不是那幾個欄位以外的裝飾，
   是稽核在告訴你出事了；省掉它們，使用者手上就只剩下說「沒事」的那幾段。

   **有內容的段落一律逐字照抄。** 只有 `pass` 與 CLI 自己的空值字可以壓縮。說「沒事」的
   段落留著最省事，說「有事」的那段才是會被刪掉的——所以這條規則是刻意不對稱的：
   **一段講的東西越多，你對它的處置自由越少。**
3. **之後另立「hub 判讀」一節**——去重，逐條標註你的初步判讀（成立／不成立＋為什麼／
   需使用者裁決）。**每一項都要標明它來自哪幾條觀察**，寫成 spoke ＋ 條號
   （`safety 2、3；feasibility 9`），而且**每一條觀察都要出現在至少一項裡**。
   兩支 spoke 的編號觀察，要嘛全部出現在那一欄，要嘛沒出現的一眼就看得出來——**這正是重點**：
   沒有編號的話，「安靜地沒被列進來」與「你判讀過但認為不成立」長得一模一樣。

### 跑了多次時怎麼合併

**取聯集，不是取交集。** 逐條標出現次數（`3/5` 這種），但**不要用出現次數當重要度**——
只出現一次的可能是嚴重級，每次都出現的也可能是假陽性。
**重要度一律由 hub 開檔驗證後自己判，不看票數。**

### 判讀時必看的三件事

**一、`run.jsonl` 的 `toolCalls[]`。** 那是「它實際讀了什麼」，不是「它說它讀了什麼」。
某個 spoke 若零次工具呼叫，它的回報只是文字審查，引用程式碼的說法要打折。

**二、安全或正確性的宣稱，自己打開檔案驗一次再轉述。** 不要把 spoke 的宣稱直接當結論
報給使用者。

**行號要重新查證。** spoke 的引用會有幾行到數十行的偏移，而**內容描述往往是對的**——
事實層可用、位置層不可用。**位置錯不等於幻覺**（幻覺是「該檔根本沒有這段」），兩者處置
不同：幻覺要重跑或換模型，位置錯只需自己重新定位。**把位置錯判成幻覺，會丟掉整份能用的
產出。**

**這條對你自己寫的行號同樣成立。** 驗完 spoke 的引用、隔幾段自己憑印象寫一次行號，
等於把漂移換上你的名字放回去——**而你的份量更重**，因為你說了你開過檔。

**三、驗 spoke 引用時，註解不算證據。** 「spoke 說某段有註解背書某個結論」不夠，還要驗
**註解說的還成不成立**——註解會與程式碼漂移，而漂移的註解讀起來跟正確的一模一樣，
只驗「註解存在且內容吻合」會把錯的判成對的。AGENTS.md 必答檢查第 1 條「不能只憑檔名、
註解或行號」原本管的是寫規劃書時，這裡把它擴到驗收 spoke 引用時。

**spoke 說「我讀不到 X 所以無法確認」是正確回報，不是假警報。** 它指出的是**你沒放進清單**的檔，
那是你的缺口、不是它的錯——把它歸到「假警報」，或自己默默查掉就往下走，
會把「清單裁錯了」這個唯一的訊號蓋掉。**你可以自己補查，但仍要明說清單當時是短的。**

### 稽核表怎麼看

| 欄位 | 意思 |
| --- | --- |
| `工具呼叫:N（允許 N／拒絕 N）` | 讀了幾次、幾次被拒——`run.jsonl` `toolCalls[]` 的統計。**印在最前面**，排在收尾句之前 |
| `收尾句` | pass／fail |
| `觀察:N` | 條數；`無法計數` 表示格式無法辨識，翻原文確認 |
| `無法驗證欄` | 有沒有照模板寫這一節。**判讀產出品質時看這欄有多具體**（例如逐項標明哪個結論依賴哪個不可讀的檔案），不要看觀察條數——條數不可靠，重疊、灌水都會推高條數但不代表品質 |
| `佔位符:<字面>×N` | 回報裡留著模板的佔位符字面（spoke 忘了填空）。**只影響該欄位的可讀性，觀察內容本身通常完好**——先翻原文確認是不是只有標題欄變成雜訊。無命中時印「無」 |

**若欄位最前面出現 `⚠ 零原始碼讀取（允許 N 檔）`**——見下方「零讀取時怎麼辦」，先處理這個
再看其他欄位。

### 為什麼「清單外引用」欄不見了

0.3.2 拿掉了這一欄，不是漏做，是三個候選問題各自有更合適的地方回答：「spoke 讀了不該讀
的檔嗎」由白名單硬擋，不必等稽核；「hub 的清單漏了嗎」由「無法驗證」欄答得更完整；剩下
「引用了沒讀過的東西嗎」需要區分**引用**與**轉述**——這是內容判斷，不該由引擎判。

這欄**至今沒抓到過真正的幻覺**：抓到的多半是 spoke 照抄素材的縮寫路徑、轉述素材裡提過但
自己標明讀不到的路徑，或絕對／相對路徑混用。

### 零讀取時怎麼辦

看到 `⚠ 零原始碼讀取` 時：

**先確認允許清單是不是空的。** 清單留空是合法設定（純文字審查），此時零讀取是預期行為，
不是異常。

**清單非空卻零讀取——判定為「這份工單沒有被執行」。**

> 不是「品質差」、不是「部分可用」，是**沒跑**。工單的問題是在「有程式碼」的前提下寫的
> （例如「現有程式碼中是否已存在可直接複用的取值路徑」），前提不成立時整組問題都失效。

**處置：整份重跑，不要分析內容、不要挑「還有用的部分」。**

發現零讀取之後還去分析報告、搶救可用的部分，**是本末倒置**。理由是資訊來源：

- spoke 只拿到工單，而**工單是你自己寫的**
- 所以報告內容只有兩種來源：**你自己寫的東西反射回來**，或**編的**
- 沒有第三類——它沒有任何你不知道的資訊管道
- **你讀到「跟我想的一樣」會覺得有價值，那是自己的回音**；而唯一「新」的部分往往正是幻覺
  （例如指名某個常數存在於某個檔，而那個檔完全沒有那個字串）

可搶救的文字層觀察，**重跑一次就會再拿到，而且是更好的版本**。重跑很便宜。

**重跑方式**：換一個型號，或重排允許清單順序後重跑（見第 3 節「跑 2–3 次怎麼做」）。
清單特別大的時候比較容易發生——重跑時順便把清單收斂到「真正回答得了這幾題的那些檔」。

最後把這次的情況告訴使用者。

---

## 7. 清理（使用者裁決完之後）

```bash
rm -rf tmp/spoke/<ticket-id> tmp/dispatch/<ticket-id>
```

**這是整套流程裡唯一會刪東西的地方，而且要等使用者裁決完、他說了才刪。** 其他任何時候
——包括派工前那個擋路的目錄——一律照第 5 節：可以問，不可以自己刪。

lens 定義留著，下次還會用。

## 出問題怎麼辦

| 症狀 | 處置 |
| --- | --- |
| 報表數值不對 | 停在 `--dry-run`，檢查 `_dispatch.md` |
| 中途失敗 | 讀 `run.jsonl` 的 `round_error` 事件（狀態碼、訊息、是第幾輪）與 `raw/<agent>.errors.json`；已完成輪次的內容仍會落檔 |
| 真失敗或逾時 | **要不要重跑問使用者，不要自行重跑**——重跑是重新付費，中斷前的花費救不回來 |
| 撞 429 | 加 `--concurrency 1` 重跑 |
| 報告品質差 | 換一個型號重跑，或同一組設定再跑一次取聯集（見第 3 節「跑 2–3 次怎麼做」） |
| 缺 API key | 使用者要在 `~/.config/dowafu/.env` 設定，**你不要去碰那個檔** |
| 找不到 `dowafu` | **查不到不代表沒安裝**——見 §1.5，多半是沙箱不讀家目錄 |
| `Operation not permitted` | host 的沙箱擋的，**不是工單或指令的問題**。照提示放行再跑一次 |

**撞到任何異常，告訴使用者**——不要自己吞掉或繞過去。
