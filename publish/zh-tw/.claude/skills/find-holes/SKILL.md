# find-holes — 找漏洞 spoke 派工

你是 hub。本 skill 把規劃書的指定範圍派給乾淨視角的 sub-agent 找漏洞。
**spoke 產出意見，不產裁決；採不採用由使用者決定。**

> **本 skill 只管內派。** 需要外部模型的異質視角、或要對照真實原始碼審查時，
> 改用 `find-holes-external`（走 `dowafu` CLI，spoke 唯讀且受白名單控管）。

## 步驟

### 1. 讀規劃書

參數指定的檔案。使用者有指定聚焦章節／問題就只取該範圍；否則取設計定案章節
（跳過背景、前情、已定案事實引用）。

### 2. 組 need-to-know 工單

只有三樣：

- **待審段落原文**——直接內嵌到 prompt，不給檔案路徑
- **前提清單**——標明「前提，不受審」：使用者已定案的決策、已驗事實的結論。
  只給結論一行，不給 facts 檔
- **具體問題**——每個 spoke 2–4 條，例如「§3.2 的配對規則在併發下有沒有洞？」

**不准放進工單**：歷史版本鏈、已廢棄的規劃文件、決策過程背景、任何 `_docs` 路徑。
先例只能以一行判準的形式給（「給尺不給屍」，見 AGENTS.md 出處三規則）。

### 3. 提出派工計畫，停下等確認

**未獲同意不得呼叫 Agent。** 依規劃內容從三個 lens 中選（全部唯讀）：

| agent | lens |
| --- | --- |
| `hole-finder-feasibility`（sonnet） | 可行性、可實作性、引用即驗證 |
| `hole-finder-safety`（opus） | 併發競態、失敗態、輸入驗證、資料洩漏 |
| `hole-finder-cost`（sonnet） | 計費呼叫閘門順序、pre-check、超限行為 |

三種都不合的規劃書，用通用 `hole-finder`（sonnet），由你在 prompt 中指定自訂 lens。

要向使用者列出的：

- 派幾個（1–3）、各自的 agent 與 lens
- 各自的模型（用 agent 預設。該次的洞需要更深推理時，可在 Agent 呼叫用 `model` 參數
  升級 opus／fable，並說明理由）
- 工單內容摘要（給了哪些段落、哪些前提、哪些問題）
- **每題的「問題 → 答案在哪個檔 → 在清單裡嗎」對照表（必列）**

不要把問題和清單分成兩塊各列一遍，那樣看不出哪一題沒有對應的檔案：

| Q | 問題 | 答案在哪個檔 | 在清單裡嗎 |
| --- | --- | --- | --- |
| 1 | §3.1 的變更可行嗎 | `prisma/schema.prisma` | ✅ |
| 2 | §2 現況描述與程式碼有無出入 | `lib/a.ts`、`lib/b.ts` | ❌ **要補** |

**這是最常犯的錯**——「問了某題，卻沒給回答那題所需要的檔」。逐題列出來，
使用者一眼就能看出漏了什麼。**這一欄不是形式，是目前唯一擋得住漏檔的機制。**

**使用者對數量／模型／lens 的修改一律照辦。**

### 3.1 確認後，每個 prompt 必含

- **工單內容**（第 2 步）
- **允許讀的程式碼檔案清單**，並明令**不得**瀏覽 `_docs/` 下的其他文件

  裁這份清單時**逐題自問：「這一題的答案在哪個檔？那個檔在清單裡嗎？」**
  按 lens 的名稱配檔案（safety 就給安全相關的）會配錯——**lens 是看的角度，
  清單是看的材料**。清單對不準問題的答案位置，spoke 物理上不可能答對。
  **漏了是派工端的失誤，不是 spoke 的問題。**

- **清單內把大檔排在最後**（依檔案大小遞增）。spoke 照清單順序讀檔，每輪會重送先前
  讀過的全部內容，所以排越前面被重複計費越多次，差距可以到將近一倍。
  內派的 context 機制不同，效果未必相同，但排序零成本、無副作用，照做不會有壞處。

- **產出格式**：「觀察＋依據（檔案:行號 或 推理）」的清單。**不得**給結論裁決、
  嚴重度分級、「應該改成」的替代設計、採用建議；不確定的寫成問題，不寫成缺陷。

### 4. 回收——摘要優先，原文為例外

每個 spoke 的回報都要讓使用者看到，標明 lens 與模型。**摘要是預設**，滿足以下四個
必要條件：

1. **明確宣告取捨**——在摘要開頭寫明「本節為摘要，非逐字照登」，不安靜地摘掉
2. **判讀涵蓋每一條，無一略過**——每個 spoke 的每一條觀察都要在後面的「hub 判讀」出現，
   這是取代「原文照登」的可稽核性來源：原文不在你眼前列出，不代表它沒被看過
3. **原文仍在這輪對話裡**——sub-agent 回傳的完整內容留在上下文中，使用者要求時可以
   重新貼出核對
4. **只在原文還找得到時才成立**——原文若已不在上下文範圍內，就沒有底本可查

> 這條規則要防的不是「沒有原文」，是**防止 hub 只挑對自己有利的講**。滿足以上四件事，
> 手段換成摘要也一樣防得住；換句話說，要守住的是目的，不是「原文」這個手段本身。

**原文照登用於兩種情形**：原文已不在上下文裡（沒有底本可查，摘要不成立），或單份規模
小到摘要反而多此一舉。除此之外都走摘要。

**做不到第 2 條就不要派這麼多 spoke**——問題出在派工規模，不在呈現方式；不要拿
「沒把握」當理由退回整份照登。

之後**另立「hub 判讀」一節**：去重，逐條標註你的初步判讀（成立／不成立＋為什麼／
需使用者裁決）。

### 5. 使用者裁決後

被採納的項目由你修訂規劃書（新版只寫差異）。**spoke 的產出永遠不直接成為文件版本。**

## 判讀 spoke 回報時必看的三件事

**一、安全或正確性的宣稱，自己打開檔案驗一次再轉述。** 不要把 spoke 的宣稱直接當結論
報給使用者。

**二、註解不算證據。**「spoke 說某段註解背書某個結論」不夠，還要驗**註解說的還成不成立**
——註解會與程式碼漂移，而漂移的註解讀起來跟正確的一模一樣。

**三、行號要重新查證。** spoke 的引用會有幾行到數十行的偏移，而**內容描述往往是對的**：
事實層可用、位置層不可用。

> **位置錯不等於幻覺。** 幻覺是「該檔根本沒有這段」，處置是重跑或換模型；
> 位置錯只需自己重新定位。把前者誤判成後者會丟掉整份能用的產出。

## 紅線

- spoke 意見**不得觸碰「做不做」**。若它寫出終止／阻擋類的結論，丟棄該結論、
  只保留其中的事實部分，並在回報中註明。
- **不得因 spoke 意見自行改規劃書的狀態欄。**
